1 · Pipeline — what actually runs

A sim agent is an ordinary player. It opens a real WebSocket, walks real chargen, and drives itself with a DR script executed by the same engine the browser client uses. There is no bot API and no privileged state access. That constraint is deliberate: every measurement bug we have hit came from observing something other than what the agent experiences. 

scripts/race-guild-sweep.mjs          driver: variants, repeats, verdicts, DB rows
  └── scripts/lib/wire-session.mjs      one WS session: auth, chargen, BFS nav, vitals
  └── scripts/lib/script-gen.mjs        builds hunt.dr / circle.dr / mega.dr per guild
  └── public/js/script-engine.js        the SAME engine the web client runs
  └── scripts/lib/stall-detect.mjs      pure verdict classifier (healthy/slow/stalled/wedged)
  └── scripts/lib/sweeps-db.mjs         history → public/live/sweeps.db
  └── data/guild-scripts.js             per-guild verbs, curricula, fidelity regexes

Per-run sequence

1. register/login over HTTP        → token
2. WS connect, charselect/create   → a fresh level-1 character
3. {t:'boost', mult:N}             → test-only speed multiplier (default 20x)
4. generate script library         → scripts_put x3 (hunt, circle, mega)
5. run mega = putrun hunt ; putrun circle
6. supervisor interlocks OUTSIDE the script (flee, rest, watchdogs, hall trips)
7. finish → verdict + grade → fidelity log + fidelity-summary.jsonl + sweeps.db
Two control layers. The script handles the routine loop (arm, walk, scan, fight, skin, hall trip). The supervisor in supervise() handles anything needing judgement — fleeing at low HP, resting, escaping a stuck room, deciding a hall trip is worthwhile. Keep new logic on the correct side: script for routine, supervisor for judgement.

2 · Generated scripts

Three scripts are generated per character and saved to the account via scripts_put, exactly as a player would save them.

ScriptRoleShape
<guild>hunt Arm, travel, scan, fight, skin, rest ARMCHECK → BUY ladder → BUY_ARMOR → ARMED → SCAN → FIGHT_<species> → SCAN_DONE
<guild>circle Guild-hall trip: learn, circle, spend TDPs, town errands HALLTRIP → learn abilities → circle → TRAIN (tdptrain) → BACK (sell/bundle)
<guild>mega One full cycle putrun hunt ; putrun circle

Barbarian fight loop (current)

SCAN:            put exp            ← readiness check, free (no RT)
                 matchre CIRCLE_READY ready to circle
                 put roar everilds_rage   ← preFight OPENER (RT is clear here)
FIGHT_rat:       put attack rat / wait
                 put analyze     / wait
                 put skin rat    / wait
SCAN_DONE:       wait ; pause 3
                 put exp            ← per-kill sheet check, free
                 iflt hp 40 goto REST
                 goto FIGHT_rat
Ordering is load-bearing. The roar used to sit after the swings. attack charges 3s of roundtime and roar is in RT_BLOCK, so it was refused 417/417 times in one run — the signature ability never executed, the fidelity check never passed, and the supernatural exp it grants never accrued. RT-blocked abilities belong before the swings.

3 · Variants — the knobs we A/B

A variant is a named parameter set applied to the generated scripts and the supervisor interlocks. Benchmark mode runs each variant N times, strictly sequentially, so concurrent agents never contend for spawns and skew timings.

VariantrestPcthallEveryarenaBand hallFallbackStateHypothesis
baseline 35424m live Control. All other variants change exactly one knob against it.
baseline_v2 35429m unproven Blind hall timer 4m → 9m. Logs showed the timer walking the full arena→hall→bazaar→arena circuit while ranks were nowhere near, burning most of a short run in transit. The rank-readiness gate still fires immediately when ranks actually qualify.
rest50 50424m unproven Rest earlier. Fewer deaths vs less time hunting.
hall8 35824m unproven Half as many hall trips — more hunting, slower TDP spend.
wide2 35644m unproven Wider creature weight class: faster exp, higher death risk.
errand ———— dropped Deleted at 0/3 healthy — but the stated reason ("couldn't enter world, account already has 5 characters") is now known to be the MAX_CHARS sweep ceiling, not the variant. Deserves a retrial. Its sell/bundle economy loop is now baseline for all variants.
Kaizen rule. One variable per variant, named after what changed, with the hypothesis written down. A variant whose diff spans several knobs cannot tell you which one mattered.

4 · Metrics & verdicts

Live verdict ladder (worst evidence wins)

VerdictTrigger
wedged Parked in one room ≥4m with ≥5 refused moves and 0 kills; or zero progress of any kind for 6m; or pinned under 25% HP for 3m; or the effort-without-progress rule (≥6 swings in 2m, no kills, no rank movement).
stalled Refusal storm (≥14 in 2m) while idle and killless; or no progress for 3m; or parked out of combat for 3m.
slow <40% of the guild kills/hour baseline, after the run has lasted 3m.
healthyNone of the above. First 2m is a grace window — never judged.

End-of-run grade

A   ≥2 circle-ups and 0 deaths
B   ≥2 circle-ups
C   ≥1 circle-up, or ≥10 kills with 0 deaths
D+  ≥5 kills and ≤1 death
D   everything else
This grade is the weak part of the system. It is dominated by circle-ups, and no barbarian run has ever produced one — so nearly every run grades C or D and the grade carries almost no signal. See §5 for what should replace it.

Circle-gap tracking (the most useful signal we have)

[gaps] 8m circle 1->2 blocked:10 shortfall:25 ranks:123 src:exp | 1st supernatural 0/2, 2nd weapon 2/8, ...
FieldMeaning
blockedHow many of the 19 circle-2 requirements are unmet.
shortfallTotal ranks still needed across all unmet slots. Watch this trend.
ranksSum of all skill ranks earned.
src exp = parsed from the exp sheet (authoritative). mindstate = fallback, understates ranks — see §7.

A shortfall that falls steadily is a working script. A shortfall that is flat for the whole run is a structural blocker, not a slow grind — that pattern is exactly how the "barbarians cannot train any supernatural skill" bug surfaced.

5 · Dropping a variant — and what to measure once it's good

The working rule is "when a script has no strength we drop it." That is right, but today the only strength signal is the grade, which is almost entirely circle-ups — and no barbarian run has produced one yet. So the honest position is: we cannot currently rank variants at all.

Drop criteria — while barbarian is still being made correct

SignalThresholdAction
Wedged / stalled rate≥2 of 3 repeats Drop — but confirm it is the variant, not infrastructure.
Shortfall trendFlat across the whole run Investigate first. Flat = structural blocker, not a bad variant.
Kills/hour<40% of the 50/h barbarian baseline Flag as slow; drop only if it repeats across ≥3 runs.
Deaths≥2 per runDrop — the interlocks are not protecting the agent.
Never drop a variant on one bad run. The errand variant was deleted at "0/3 healthy" for a reason that turned out to be a harness ceiling affecting any variant that ran late in the ordering. Before dropping, confirm: world still up? zero reconnects? distinct account per run? shortfall actually flat? If any of those fail, the run measured the harness, not the script.

Better metrics — once barbarian reliably circles

These replace the grade as the ranking signal. None are implemented yet.

MetricDefinitionWhy it beats the grade
Ranks per hour Total skill ranks ÷ run hours Continuous and always available, unlike a circle-up that may never happen.
Shortfall closure rate Ranks of shortfall eliminated per minute Directly measures progress toward the actual goal; predicts time-to-circle.
Projected time-to-circle Current shortfall ÷ closure rate Lets a 10-minute run rank variants without waiting 25 minutes for a circle.
Blocked-slot count Unmet requirements remaining Falls in visible steps; distinguishes "grinding" from "stuck on one slot".
Transit fraction Time in town/hall rooms ÷ total Directly measures the waste hallFallbackMs targets.
Fidelity coverage Signature checks passed ÷ total Catches "fights fine but isn't playing its guild" — the roar bug scored 0/2 for weeks.
Silver efficiency Gear value acquired ÷ silver earned Tests whether the economy loop actually converts loot into capability.
Sequencing. Ranking variants is pointless until one variant reliably reaches circle 2. Get barbarian clearly correct first, then add the metrics above, then re-run the full variant matrix.

7 · Measurement lessons (each cost real time)

TrapSymptomRule
Mindstate feed is pool-gated parry 0/8 for a character at rank 8 Ranks come from exp. A skill with an empty pool vanishes from mindstate; absent ≠ zero.
Fidelity log has a verb allowlist "0 learn commands" while they were executing fine Absence from the log is not absence from the wire. Add new verbs to the allowlist.
Death respawns at full HP Test failed with the player mysteriously at 72/72 Check the end result, not hp <= 0 after the fact.
RT refusals are ambient noise 922 "must wait" lines looked like the roar bug's cause Read the actual failure reply, not the nearest plausible one.
Stale log sections Diagnosed a wedge from a previous run's lines Anchor on the last === sweep run marker before drawing conclusions.
Tests can encode bugs tdp-afford asserted the always-refused roar ordering When a test blocks a verified fix, check whether the test is wrong.
moves() takes edge objects Generated move undefined Paths are {dir,to} from bfsPath, not strings.
gainSkillExp banks to expPools Working fix looked inert via skills[id].exp Assert on p.expPools[skill]; ranks only move on pulses.
Standing rule. Prefer player-visible information the agent could legitimately obtain (exp, inventory — both free of roundtime) over reading state out of SQLite. Side-channels hide exactly the bugs we are hunting; the DB is for verifying a claim, never for driving agent decisions.

8 · Running it

# single guild, one variant, long enough to actually circle
node scripts/race-guild-sweep.mjs --benchmark barbarian \
  --variants baseline --races giantman --repeats 1 --minutes 30

# A/B two variants, 3 repeats each
node scripts/race-guild-sweep.mjs --benchmark barbarian \
  --variants baseline,baseline_v2 --races giantman --repeats 3 --minutes 25

# read history back as a table
node scripts/race-guild-sweep.mjs --report

# watch a run live
tail -f public/live/fidelity-barbarian-baseline-giantman.log
grep -E '\[gaps\]' public/live/fidelity-barbarian-baseline-giantman.log

Pre-flight checklist

  • World up on :3000 and freshly restarted if server code changed.
  • --minutes ≥25 for circle-2 attempts; shorter runs cannot reach it.
  • After the run: confirm 0 crashes, 0 reconnects, and one distinct account per run before trusting any number.
